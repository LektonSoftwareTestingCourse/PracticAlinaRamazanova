# Submission Guide — курс тестирования ПО, ИТМО

> **Важно:** PR не используется для сдачи студенческих работ. Студенческие тесты не предназначены для слияния в `main`. Сдача — через Issue с label.

## Общий workflow

1. **Создать ветку** `practice-{N}-{surname}` от `main` (например, `practice-2-ivanov`)
2. **Выполнить задание**, разместив артефакты по путям согласно таблице ниже
3. **Запушить ветку** — CI проверит автоматически (сборка, линтеры, тесты, smoke)
4. **Создать Issue** с заголовком «Практика N — Фамилия», label `practice-N`
5. В теле Issue указать:
   - Ссылку на ветку
   - Путь к артефакту
   - **Полное содержимое артефакта** (для LLM-проверки)
6. Преподаватель проверяет: CI-статус (для кодовых практик) + LLM-прогон (для текстовых)
7. Результат — в комментарии к Issue

| Джоба | Что делает | Какие практики |

## `load-smoke` — как работает

**Нагрузочное тестирование выполняется локально.** CI проверяет только работоспособность скрипта (smoke-уровень).

### Локально (студент)

Студент создаёт скрипт [`scripts/load-smoke.sh`](scripts/load-smoke.sh) в своей ветке и запускает его на своей машине:

1. `docker compose up -d`
2. Генерирует тестовые карты (`POST /api/cards/generate`)
3. Запускает `scripts/load-smoke.sh` с `LOAD_COUNT=500` (или своим значением)
4. Собирает метрики (p50/p95/p99, throughput, error rate, avg response time)
5. Описывает результаты локального прогона в [`docs/practice-6/test-summary.md`](docs/practice-6/)

Студент **сам определяет**: сценарий, количество транзакций, собираемые метрики.

### В CI (автопроверка)

CI-джоба `load-smoke` делает **smoke-проверку** скрипта:

1. Поднимает docker compose
2. Генерирует тестовые карты
3. Запускает `scripts/load-smoke.sh` с `LOAD_COUNT=10` (smoke-уровень — только проверка, что скрипт не сломан)
4. Если скрипт завершился без ошибок — ✅ OK
5. Если скрипт отсутствует — CI выводит предупреждение, но не фейлит билд

> **Почему не 500 в CI:** GitHub Actions раннеры (2 ядра, 7 GB RAM) не обеспечивают стабильных метрик для нагрузочного тестирования. Реальные замеры — только локально.

## Как работает LLM-проверка (промежуточный вариант)

> **Текущий статус:** промежуточный шаг перед полной автоматизацией через GitHub Actions + LLM API.

1. Студент копирует **полное содержимое артефакта** в тело Issue
2. Преподаватель копирует Issue-текст + промпт (предоставляется преподавателем) → отправляет в LLM (ChatGPT / DeepSeek / Claude)
3. LLM возвращает JSON с оценкой по рубрике
4. Преподаватель копирует JSON-результат в комментарий к Issue
5. Если `needs_manual_review: true` — преподаватель проверяет вручную и добавляет label `needs-review`

## Часто задаваемые вопросы

### Почему не PR?

Студенческие тесты и артефакты не предназначены для слияния в `main`. `main` содержит production-код СМП (системы массового процессинга). Студенческие ветки — изолированные workspace'ы для выполнения заданий. Issue + label обеспечивает прослеживаемость сдачи без засорения основной ветки.

### Как узнать, что CI прошёл?

После пуша откройте вкладку Actions в репозитории — вы увидите статус пайплайна для вашей ветки. Зелёный — всё хорошо, красный — нужно поправить ошибки и запушить снова.

### Где смотреть результаты LLM-проверки?

Преподаватель публикует JSON-результат в комментарии к вашему Issue. Там же будет указано, нужно ли что-то доработать.
