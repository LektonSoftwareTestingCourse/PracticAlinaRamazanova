# Тестовая стратегия СМП

## 1. Цель

Проверить, что СМП корректно обрабатывает транзакции по цепочке от Gateway до Authorization, Card Management и Transaction Logger: принимает правильные решения APPROVED/DECLINED, возвращает корректные коды, соблюдает лимиты и баланс и не теряет транзакции.

Подход риск-ориентированный: чем выше риск для денег, данных и основной цепочки, тем глубже проверка. Полный тест-дизайн применяется к Authorization и Card-Management, остальные сервисы покрываются чек-листами и сквозными сценариями.

## 2. Уровни проверок

| Уровень | Что проверяется |
|---|---|
| Статический | ТЗ, требования, классы и границы |
| Smoke | Запуск сервисов и базовая транзакция |
| Unit | Бизнес-логика Authorization и Card Management |
| API | REST-контракты, валидация, коды отказа |
| Интеграционный | PostgreSQL, RabbitMQ, outbox, отказ зависимостей |
| E2E | Основные сценарии покупки и отказов |
| Нагрузочный smoke | 500+ транзакций и параллельные резервы |

## 3. Приоритеты и риски

| Приоритет | Что проверяется |
|---|---|
| P1 | Authorization, Card Management, критическая цепочка, баланс, лимиты, коды отказа |
| P2 | Gateway, Bin Lookup, Notification Service, интеграционные отказы |
| P3 | Симуляторы и Dashboard |

Основные риски: неверное решение об авторизации, списание сверх баланса, потеря/дублирование транзакций, ошибки при отказе RabbitMQ или зависимых сервисов.

## 4. Область тестирования

**Входит:** все 11 сервисов по ТЗ и API; транзакции; лимиты и баланс; HTTP и RabbitMQ; outbox; отказ зависимостей; базовая нагрузка.

**Не входит:** PCI DSS и реальные PAN/BIN, реальные банки и платёжные системы, полноценный ISO 8583, stress/soak, HA/DR и кросс-браузерная проверка Dashboard. Причина — учебная замкнутая система и ограниченный объём практики.

## 5. Техники

Для Authorization и Card-Management используются:
- классы эквивалентности;
- граничные значения;
- попарное тестирование PICT.

Для остальных сервисов используются чек-листы и сценарии критического пути.
